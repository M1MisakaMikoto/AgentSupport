# 迁移指南：v0.2 → v0.3（Temporal 执行层）

本文记录从自研 `distributed` 编排（ExecutionJob / RunCommand / checkpoint 表）
迁移到 Temporal 执行层（`execution_mode=temporal`）的共存与切换步骤。
设计决策见 `docs/adr/003-temporal-execution.md`，验收门禁见
`docs/testing/api-full-test-plan.md` 与 `tests/integration/temporal/`。

## 1. 目标形态

- **编排层**：`RunSessionWorkflow`（workflow_id = run_id）+ 四个 Activity
  （`start_runner` / `execute_run` / `resume_run` / `stop_runner`）+ Signal
  （`submit_input` / `submit_approval` / `cancel_run`）。
- **会话层**：Trae 会话重建协议保留（`agent_runner_contracts.checkpoint`），
  作为段快照数据契约。
- **对外契约**：API、SSE 事件流、事件序列语义不变。

## 2. 阶段 0：并行原型（已完成）

`execution_mode=temporal` 与既有模式并存。控制面通过 `TemporalRunCoordinator`
启动 workflow / 发信号；事件与状态经 `repository.append_event` 落库。
验收：`tests/integration/temporal/` 5 个用例通过（无 dev server 时自动跳过）；
全量测试无回归。

## 3. 阶段 1：灰度切流

**共存约束**

- 一个部署实例内，API 的 `AGENTSUPPORT_EXECUTION_MODE` 决定新 conversation 走哪条
  执行路径：`temporal` → workflow；`distributed` → 旧 Job/Worker。
- 存量 in-flight run 继续由旧 `worker` 服务处理；切换只影响**新创建**的
  conversation。
- 两类 run 共用 PostgreSQL（conversation / 事件 / workspace / skills），互不干扰；
  事件表结构不变。
- 需要一台可达的 Temporal（compose 的 `temporal` dev 服务或生产部署），
  API 与 `temporal-worker` 通过 `AGENTSUPPORT_TEMPORAL_HOST` 指向同一实例。

**切换步骤（按环境）**

1. 部署 `temporal` 服务（或配置 Temporal Cloud）。
2. 启动 `temporal-worker`（compose `temporal-worker` 或 K8s
   `deploy/kubernetes/temporal-worker.yaml`）。
3. 将目标环境的 API 设为 `AGENTSUPPORT_EXECUTION_MODE=temporal`。
4. 观察新 run 事件序列与旧 run 一致（里程碑：`interaction.requested` →
   `approval.decided` → `run.completed`），完成率无回退后推进阶段 2。

**回滚**：将 API 环境变量改回 `distributed` 即可；存量 conversation 不受影响。

## 4. 阶段 2：退役（在阶段 1 稳定后进行）

- 删除 `execution_jobs` / `run_commands` / `runner_endpoints` /
  `conversation_checkpoints` 表与对应 repository 方法。
- `reconciler` 收敛为孤儿容器清理；`worker` 进程移除，改由 `temporal-worker`
  承担执行。
- 新增 alembic 迁移 drop 上述表；迁移前确认无存量 distributed run。

## 5. 验收门禁

- `tests/integration/temporal/` 全绿是接入前提。
- 阶段 1：`test_dual_run_parity_same_milestones` 证明旧/新执行层对同一确定性
  任务给出相同里程碑事件序列与终态。
- 对外契约（API、SSE、事件序列）零变化：现有契约套件保持全绿。
- 阶段 2 后：崩溃恢复场景（杀 Worker / 杀容器）可重复演示，损失上限为段粒度。

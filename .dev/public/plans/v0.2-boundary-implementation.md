# v0.2 边界落地实施计划（草案）

Status: completed（已实现并随 `0.2.0` 发布）
Date: 2026-08-11
关联: [ADR-002](../../docs/adr/002-platform-boundary-and-api-v2.md)、
[AgentSupport API 参考](../../docs/api/agentsupport-api.md)

## 目标

按 B+ 边界把 v0.1 演进为 v0.2（破坏性版本 `0.2.0`）：先落地 Provider 抽象与 Runner 注册
（共享 token 鉴权），再按删除清单清理公共 API，完成数据迁移、部署与文档同步。

## 决策摘要（已收敛）

1. 平台只管理执行资源（Workspace / Session / Conversation）与执行配置，业务实体交给上游。
2. 标签：`tenant_id` / `user_id` / `project_id` 结构化可选 + `metadata` 兜底，不校验存在性；
   事件顶层携带；无标签资源计入 default/unknown 无头统计。
3. auto-create：仅显式传入且不存在的 workspace / session ID 补建，绝不生成缺失字段；
   默认开启，生产可关；ID 准确性由上游负责。
4. 执行配置由调用方随请求传入（复用 `ProjectConfig`），平台不再管理 preset 模板。
5. Provider 抽象与 Runner 注册 / 心跳 / 注销纳入内部契约；鉴权用共享 token。
6. 版本策略：直接替换根路径，不保留 v1；发布 `0.2.0`。
7. 生命周期 API（PATCH / DELETE / pause / resume）本轮仅写入契约，不实现。

## 阶段划分

### Phase 0：基线

- 合入/确认工作区未提交的 retention、idempotency 改动，作为 v0.2 基线。
- 固化 v0.1 契约测试快照（删除清单的对照依据）；补齐 v0.2 契约测试骨架。

### Phase 1：Runner 注册协议 + token 鉴权（provider 抽象最小闭环）

目的：控制面不再假设固定 Runner 地址或单一 Trae 实例；Runner 自注册、心跳、注销，
控制面按能力路由。

改动点：

- `agent_runner_contracts`：新增注册 / 心跳 wire 模型（provider、endpoint、version、
  capabilities、heartbeat、status）；capabilities 沿用 run / input / checkpoint / cancel /
  events / resume。
- `session_runner`：新增注册客户端（启动注册、周期心跳、关闭注销）；新增
  `SESSION_RUNNER_TOKEN` 配置。
- `agentsupport`：RunnerRegistry 端口 + 内存 / SQLAlchemy 实现（`runner_endpoints` 表已存在，
  补齐 token_hash、last_heartbeat、status、provider 字段）；注册 / 心跳 / 注销内部路由，
  校验 `X-Runner-Token`（恒定时间比较，token 不进日志）。
- 调度路由：创建 Run 时按 provider / capabilities 选择已注册 Runner；`/cores` 改为动态查询
  注册表。
- Reconciler：心跳超时（默认 30s）标记 stale / LOST 并清理端点。
- 部署：控制面 `AGENTSUPPORT_RUNNER_TOKEN`、Runner `SESSION_RUNNER_TOKEN`，Compose 与
  Kubernetes Secret 注入；跨网络部署必须经 HTTPS 入口传输 token。
- 升级空间：token 校验收敛到独立依赖层，后续可替换为 mTLS 而不改协议。

验收：

- 无 token / 错误 token 的注册、心跳、注销被拒绝（401/403）。
- token 正确时可注册、心跳、注销；过期心跳被 Reconciler 清理。
- deterministic Runner 注册后 `/cores` 动态可见，任务路由到该 Runner。
- token 不出现在日志、事件与指标中。

### Phase 2：公共 API 清理（破坏性变更）

删除：

- `/organizations`、`/users`、`/presets`、`/projects` 全部路由、schemas 与 service 方法。
- 业务实体 auto-create 与 `PRESET_*` / `USER_*` / `PROJECT_*` / `ORGANIZATION_*` 错误码。
- 配置项 `AGENTSUPPORT_DEFAULT_WORKSPACE_ID`、`AGENTSUPPORT_DEFAULT_USER_ID`、
  `AGENTSUPPORT_AUTO_RESOURCE_NAME`；`AGENTSUPPORT_AUTO_CREATE_SCOPES` 收窄为
  `workspace,session`。

auto-create 语义收窄（按 ADR 细则）：

- 仅显式传入且不存在的 workspace_id / session_id 补建；绝不生成缺失字段；
  `parent_conversation_id` 严格 404；并发补建同一 ID 原子收敛。
- 默认 `true` 保留，生产文档建议 `false`。

标签与配置透传：

- Session 增加 `tenant_id`、`user_id`（`project_id` 已有）与 `metadata` 字段；
  身份头 `X-Tenant-Id` / `X-User-Id` / `X-Project-Id` 优先级高于请求体。
- 事件顶层携带三个标签字段。
- `POST /sessions` 接受 `config`（复用 `ProjectConfig`），透传给 Runner；
  移除 preset 导入路径，缺省使用部署默认配置。

Session 级 SSE（建议本轮包含，成本低）：

- 在已有 `GET /sessions/{id}/events` 聚合轮询基础上补 `GET /sessions/{id}/events/stream`。

验收：

- v0.2 路由面与删除清单一致，旧业务路由返回 404。
- 标签过滤、事件标签、无标签 default/unknown 行为符合契约。
- 全量测试套件与 Ruff 通过。

### Phase 3：数据迁移与部署

- Alembic 迁移：sessions 表加 `tenant_id` / `user_id` / `metadata` 列；
  runner_endpoints 表补 token_hash / status / last_heartbeat / provider（若 Phase 1 未含）。
- 回填：`session.user_id` ← project.user_id；`session.tenant_id` ← 所属 user 的 organization；
  无来源置空（default/unknown）。
- 下线业务表：organizations / users / presets / projects 冻结 → 确认无引用 → 删除。
- 部署与文档：compose / k8s 增加 Runner token Secret；README、API 参考、
  上游迁移指南（删除接口、标签约定、auto-create 语义、config 透传）。

### Phase 4：devtools 调试控制台重构（上游示范）

目标：控制台"示范"板块从 v0.1 业务 CRUD 用法改为 v0.2 标签式上游用法，
不再调用已删除的组织 / 用户 / 项目 / 预设接口。

改动点：

- 移除组织 / 用户 / 项目 / 预设管理页面与对应 API 调用。
- Agent 工作台：创建 Workspace / Session 时携带 `tenant_id` / `user_id` / `project_id`
  标签与 `config`；事件轨道展示标签；保留 input / approval / cancel 流程。
- 部署板块的 API 验收套件同步 v0.2 路由面与删除清单。

验收：控制台全部示范流程走 v0.2 公共 API，无业务 CRUD 调用残留。

### Phase 5：端到端验证与发布

- 端到端测试：Compose 全栈（postgres / redis / api / worker / reconciler / retention /
  runner）跑通注册 + token 鉴权、任务提交、事件、审批 / 取消、checkpoint 恢复、伸缩、
  保留清理。
- devtools 控制台验收套件通过；全量 pytest 与 Ruff 通过。
- 发布 `0.2.0`，上游迁移指南随版本发布。

### 后续迭代（仅契约已定）

- 生命周期 API：Workspace / Session 的 PATCH / DELETE、pause / resume。
- 容量 / 配额：按 tenant 并发配额、运行时调整 `max_active_sessions`。
- mTLS 升级（按需）。

## 风险与依赖

- 删除业务 CRUD 是破坏性变更：发布前需与上游确认迁移窗口与回退策略。
- auto-create 默认开启：生产文档强调关闭；拼写错误责任归上游（已定）。
- Runner 注册依赖网络可达：跨网络部署必须 TLS 入口，token 不落日志。
- 工作区未提交改动需先合入或纳入 Phase 0 基线，避免与 v0.2 冲突。

## 执行顺序

Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5。
Phase 1 与 Phase 2 代码可并行开发，但契约测试必须先行。
